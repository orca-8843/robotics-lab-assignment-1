# Experiment: Namespaces and Topic Remapping in ROS

**1. List of Topics**

The topics `/bot1/Greetings` and `/bot2/Greetings` are created by running the same publisher program under different namespaces. This keeps the communication of the two bots separate.

**2. Topic Remapping**

The subscriber is remapped to `/bot1/Greetings` using the command `Greetings:=/bot1/Greetings`. Therefore, it receives messages only from Bot 1 and not from Bot 2.

**3. Observation of rqt_graph**

The ROS graph shows two publisher nodes under the namespaces `/bot1` and `/bot2`. Each publisher sends messages to its own greeting topic. The subscriber connects only to `/bot1/Greetings`. This demonstrates the use of namespaces and topic remapping in ROS.

**4. Conclusion**

Namespaces allow multiple instances of the same ROS node to run with separate topic names. Topic remapping redirects a subscriber to a specific topic without modifying the source code. These features help organize communication between multiple robots in ROS.

# Experiment: Topic Latching in ROS

**1. Publisher Node with latch=False**

A publisher node was created to publish the message "System Ready" on the topic `/robot_status` only once when it starts. The publisher was configured with `latch=False` and kept running using `rospy.spin()`.

**2. Observation with latch=False**

When the subscriber was started after the publisher had already published its message, it did not receive "System Ready". This is because `latch=False` does not retain the last published message for subscribers that connect later.

**3. Observation with latch=True**

After modifying the publisher to use `latch=True`, the subscriber received "System Ready" even though it was started after the publisher had sent the message. This is because ROS retains the last published message and sends it to newly connected subscribers. The publisher still publishes the message only once.

**4. Topic Information**

The command `rostopic info /robot_status` displays the topic type, publisher node, and subscriber node. The topic type is `std_msgs/String`.

**Conclusion**

Topic latching allows a ROS publisher to retain its last published message for new subscribers. With `latch=False`, late subscribers miss previously published messages. With `latch=True`, late subscribers receive the last message when they connect.
